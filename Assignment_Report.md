The Blockers and Fixes
----------------------------------------------------------------

1. FEATURES_REPLY AssertionError in _readzs()
   - Root cause: oswitch.py sent structurally invalid FEATURES_REPLY
   - Bug 1: n_buffers packed as 4 bytes (L), correct; was 1 byte (B).
            Body must be 24 bytes (!QLB3xII), not 21.
   - Bug 2: Port description had 8 config fields instead of 6
            (ofp_phy_port is 48 bytes, not 52).

2. FLOW_MOD cookie field
   - cookie was packed as 4 bytes (I); OpenFlow 1.0 defines it as 8 (Q).
     This shifted every following field.
   - Command section is !QHHHHLHH (24 bytes), not !IHHHHHIHH.

3. STATS_REPLY layout
   - Was: 1056-byte descriptor, then 4-byte type/flags.
   - Correct: header(8) + type(2) + flags(2) + body.
   - The old layout only ever parsed by accident, because the descriptor is
     all zero bytes so POX read type=0/flags=0 by coincidence.

4. ofp_match alignment
   - 40 bytes, with two pads (after dl_vlan_pcp and after nw_proto).
   - A 36-byte match is silently mis-parsed by POX.

5. Wildcard bit numbers
   - POX uses OFPFW_DL_TYPE = 16; the OpenFlow 1.0 spec text says 0x1000.
     Mixing the two turns every match into a wildcard.
     oswitch.py follows POX (its only controller), and a test asserts this.

6. ifconfig shim for Mininet
   - System has iproute2 but Mininet uses ifconfig.
   - shim/ifconfig translates ifconfig → ip.

7. 100% ping drop in end-to-end Mininet
   - oswitch bound AF_PACKET sockets with protocol 0x0003 instead of
     socket.htons(0x0003). The unconverted value yields a socket that never
     receives anything — no error is reported.
   - Mininet may also leave veth ports down; oswitch now runs
     `ip link set <iface> up` before binding, else recv() gives ENETDOWN.

8. `mn --batch` does not exist in this Mininet
   - This is Mininet 2.3-era. `--post <file>` reads CLI commands from a
     file, but it runs the INTERACTIVE CLI first, so stdin must be at EOF
     (`< /dev/null`) or the run hangs.

9. mnexec stale timestamp
   - `make mnexec` reported "up to date" while the binary did not exist,
     so Mininet hung spawning node shells. Fix: rm + make mnexec.

10. topo2.py __file__ under `mn --custom`
   - Mininet exec()s the custom file, so __file__ may be undefined.
   - _project_dir() falls back to the current working directory.

PART 2: Intent-based Networking
================================================================

Deliverable:
- intent_to_policy.py .................... LLM intent parser
- tests/test_intent_to_policy.py ........ 31 tests

The script converts natural language intent into POX-compatible firewall rules.
Parsing is done by the LLM only; an unreachable or unusable LLM causes a
non-zero exit with no policy file written.

Model: qwen2.5:0.5b (default), Phi-3 selectable with --model phi3

  - Served by Ollama (default: http://localhost:11434/api/generate)
  - System prompt fixes the h1..h4 → MAC mapping and shows worked examples
  - temperature 0.0 for reproducible output; think:false (no reasoning)
  - The whole request is sent as ONE call by default (joined from the
    individual sentences); --per-sentence restores one-call-per-intent
  - Output validated (MAC format, known host, DROP/ALLOW, phantom rules)
    before being written
  - Fails loudly on non-HTTP-200, invalid JSON, or no usable rules

Output Formats:
  - Plain text: firewall_rules.rules (src_mac dst_mac action per line)
  - JSON: [{"rule": 1, "src_mac": "...", "dst_mac": "...", "action": "DROP"}]

Usage Examples:
  python3 intent_to_policy.py "Block h1 from h3"
  python3 intent_to_policy.py "Block h1 from h3" "Block h2 from h4"
  python3 intent_to_policy.py --model phi3 "Block h1 from h3"
  python3 intent_to_policy.py -f json "Block h1 from h3"

Note on the reverse direction (h3->h1, h4->h2):
  These fail as a *consequence* of the DROP rules, not independently.
  No rule names h3->h1 — is_blocked(h3, h1) is False. Blocking h1->h3
  discards h1's ARP replies to h3, because an ARP frame is an Ethernet
  frame from h1 to h3 and the rule matches on MAC pairs alone. h3 can
  therefore never resolve h1's MAC, so the neighbour entry stays
  INCOMPLETE and the echo request is never sent. The run shows this
  directly: the pings fail with "Destination Host Unreachable", which is
  an ARP failure rather than a policy block.

  Independently, an ICMP echo *reply* is itself a frame from h1 to h3, so
  it is dropped by the same rule even with ARP resolved. A one-way
  MAC-pair drop therefore yields a *symmetric* blackout, and 33% rather
  than 17% is the honest number.

Deviation implemented, measured, and reverted:
  Exempting ARP and letting ICMP echo replies through does produce 10/12
  (only h1->h3 and h2->h4 fail; both reverse directions pass). It was not
  shipped, for two reasons:

    1. OpenFlow 1.0's ofp_match has no ICMP-type field, so no flow entry
       can distinguish a reply from a request. Letting replies through
       requires dropping the proactive flow entries and deciding every
       packet in the controller — which contradicts the assignment's
       requirement to "install the corresponding drop rules proactively
       in the switch".
    2. The relaxation produced a real policy bypass. A flow entry matches
       on MACs alone, so caching a forwarding decision for (h1,h3) while
       forwarding an echo reply also let h1's echo *request* through
       uninspected. pingall reported the pair as blocked while a direct
       `h1 ping h3` in the same session succeeded.

  The literal reading is what ships: drop every frame matching a
  prohibited pair. tests/test_firewall.py pins this down, including an
  assertion that is_blocked() still takes only (src, dst), so the scope
  cannot be widened by accident.

pingall stability:
  Deterministic once the FEATURES_REPLY bug was fixed. Six consecutive runs
  (three per network instance) all returned "33% dropped (8/12 received)".
